## 3. RAG Ingestion Flow

KnowledgeDocumentLoader → TikaDocumentReader / TextReader → 带安全 metadata 的 Document → KnowledgeIndexService / TokenTextSplitter → Ollama EmbeddingModel → SimpleVectorStore → 私有 JSON / manifest。

## 4. RAG Query Flow

Question → QuestionAnswerAdvisor → KnowledgeSearchService 的只读 adapter → Query Embedding → Similarity Search / Threshold / TopK → 来源标题和 Chunk Context → 增强 User Prompt → ChatModel → Answer。无命中时终止于固定证据不足响应。

## 5. Chat vs Embedding

代码保留 OpenAI-compatible Chat integration；真实验证的 Chat 为 Ollama `/v1` 上的 `qwen3:8b`，Embedding 为原生 Ollama integration 的 `bge-m3`。Chat 与 Embedding 使用独立配置，Chat 可换为 DeepSeek / OpenRouter，无需跟着更换 Embedding。

## 6. Chunk Configuration

默认 chunkSize=800、minChunkSizeChars=350、minChunkLengthToEmbed=10、maxNumChunks=5000、keepSeparator=true；标点是中文句号/问号/叹号/分号、换行及英文 .?!;。真实提取比较了 400/800：1609/829 块。400 和 800 都实际完成全库 Embedding，并对相同六个问题进行检索。400 临时索引：1609 块、1024 维、169308ms、24511252 bytes；800：829 块、162471ms、13387968 bytes。这只是本机单次实验，不是控制变量的性能基准。

## 12. Memory / Tool / RAG Boundary

Memory 只在 `/api/agent` 恢复短期对话；Running Tools 查询真实或测试配置的结构化活动；RAG 只在 Knowledge API 检索书籍，无 conversationId、无 @Tool、无全局 QA Advisor。

## 13. Why activities.json is not RAG

全年统计要求完整记录和精确聚合，TopK 片段会漏记录，语义相似度不能保证算术正确。因此继续由 Java RunningDataService 计算，不让 LLM 用检索片段自行求和。

## 14. QuestionAnswerAdvisor

实际代码中，它按当前问题调用可观察的 VectorStore adapter，将检索到的来源标签/文本拼接到 User Prompt，只在该次 Knowledge QA 生效。Adapter 空结果会抛内部异常，由 QA Service 返回确定的证据不足响应；离线测试证明这时 ChatModel.call 不执行。

## 15. SimpleVectorStore Limitation

整个 JSON 装入内存、逐项计算余弦相似度，仅适合本地学习/Demo，Not for production。未来可能换 Elasticsearch 获得更适合规模化检索的存储和索引能力；本阶段不做迁移。

## 20. Design Decisions

Chat 与 Embedding 解耦，因为生成与语义表示是不同能力。BGE-M3 支持中文/多语言，本地使用保护知识文本；SimpleVectorStore 足够观察当前闭环。原书和向量 JSON 含正文，只能留本机。确定性活动统计继续用 Tools。Hybrid、Reranker、Agentic RAG、RAG Tool 和全局 QA Advisor 都会扩大本阶段范围，未实现。

## 21. RAG Failure Analysis

正确知识未召回：检查提取、切块、Embedding、Query、TopK、Threshold。正确 Context 已召回但回答错误：检查 Prompt、ChatModel、来源混淆和 Context Noise。Score 不是可信概率；本地 search preview / chunkId 与 queryId 帮助定位。

## 22. v0.5 与 v0.4 的本质区别

v0.4 从 conversationId 的近期消息恢复“我们聊过什么”；v0.5 按当前问题从外部知识源检索“文档里有什么”。两者都增加模型输入 Context，但来源、生命周期和可信用途不同。
